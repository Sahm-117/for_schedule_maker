In thirty seconds

One app, three audiences, one database

FOF Ops is a phone-installable web app (a PWA). It replaced spreadsheets, group-chat lists and a printed schedule. Older names for the same thing: the repo for_schedule_maker, the Vercel site for-schedule-maker and the Supabase project "FOF Schedule Editor". Don't rename them: links, installed phone apps and backups depend on them.

3apps in one

Admin back office, the support app and the participant app, chosen at sign-in by role.

100+numbered rules

The business rules, each with where it is enforced. FLOW_MAP.md section 4.

18server functions

Notifications, reminders, the form feed, Telegram, AI help, the public API (one more is retired).

100+handoff notes

One per piece of work: what changed, what is live, what is still open. docs/handoffs/.

Risks

What could hurt the programme, and what to do about it

Checked on 30 October 2026 against the live database, then again after the fixes that day. Open risks first, then what is done.

Medium · re-check Sun 1 Nov

The app slows down when many people use it at once

What we saw

On Sunday 11 October (Cohort 10's first class) the app lagged during class, when attendance marks and notifications came in bursts (around 9:30 and 10:15). Many unrelated screens share the same worst time, about 2.8 seconds, which means the whole database stalled, not one slow screen. The database runs on Supabase's smallest free instance (shared CPU). Measured on a quiet database, each screen's question takes only 1 to 9 ms; the slow averages come from those stalls.

Done, and what is left

The biggest cause is gone (the live-update feed, below), and on Sunday mornings the background checks nobody waits on (bells, unread dots, the prayer signal, Practice's background beat) run half as often. Upgrading is not affordable. If it still stalls, the free option that fits is Oracle Cloud's Always Free server (4 CPUs, 24 GB) running Supabase ourselves, which is a project of its own. Neon and Appwrite's free plans don't fit. First, check the database numbers after Sunday 1 November.

Watch

Background checks, and Practice left on

What we saw

Practice, corporate prayer and notification checks run tens of thousands of times. Practice is switched on for all 47 supports, but only one used it in the last day, and every open app still checks it every 20 seconds.

Done, and what is left

Sunday 7 am to 2 pm: the bells, unread dots, prayer signal, update check and Practice's background beat wait twice as long; Home, a live register, meetings and walkthroughs keep their pace. The Supports page asks for everyone's last-active time in one call, and Scriptures loads 2.6 MB of previews instead of 14 MB. Left for the owner: switch Practice off when nobody is training.

Watch

Every notification goes through one queue in the database

What we saw

Pushes, Telegram and reminders are sent from the database through its web-request queue. Cleaning that queue averaged 93 ms and once hit 8.8 seconds, mostly while the database was clogged by the live-update feed.

Done, and what is left

Checked on 30 October: about 13 requests an hour, and a broadcast makes at most 10 Telegram copies, because only 10 people have Telegram on. Nothing to change now; look again if the queue grows.

Watch

One test-free database, one person, a few free accounts

What we saw

Local work and every test touch live data. Vercel's free plan caps deploys a day. The daily checks depend on one cron-job.org login.

What to do

Keep two owners on every account and every secret in Bitwarden. Batch pushes. Use test accounts and clean up.

Done 30 Oct

Live updates were the biggest single cost

What we saw

Supabase's live-update feed used about 43% of all database time since February, more than any other single thing. The app stopped listening on 10 October, but the notifications table was still on the feed.

Done

The notifications table is off the feed, which now has no tables. The feed's database check has not run once since; the bell checks for news on its own.

Done 30 Oct

Code checks didn't stop a bad deploy

What we saw

The build passed while the type check had 7 errors. There were no automated tests; every check was by hand in a browser.

Done, and what is left

The 7 errors are fixed, and npm run build runs the type check and 12 rule tests (attendance marks, completion, the Right now line, rest weeks, Sunday polling) before building, so Vercel refuses a broken deploy. Still open: older lint warnings, and the tests don't cover database functions.

Security

How the platform keeps people's data safe

Checked against the live system on 30 October 2026. What is in place, layer by layer.

Signing in

Passwords are hashed

Staff and participant passwords are stored only as bcrypt hashes, and the hash columns can't be read through the app's data API.

Sessions can't be stolen from the database

Each sign-in gets a random token. The database keeps only its SHA-256 fingerprint, and the token expires after 90 days unused.

Participants sign in by phone

With a password or a one-time code their support issues. Several people on one number each get their own profile.

The handover pages are locked

This primer sits behind one shared password (Cloudflare). The password lives in Bitwarden.

Who sees what

Every table is locked

All 156 tables have row-level security on. No table is open to anyone who isn't signed in.

The database checks every request

Reads and writes go through 467 database functions that check the session's role first. Each has a fixed search path, so it can't be tricked into running other code.

Roles and permissions

Admin, Support, Team member and custom roles with a per-page grid. Church app access and Roles are for full admins only.

Teens are protected

Teens are seen by their own Teen Support. Church apps need a separate permission to see teen details in full.

Server functions and other apps

Server functions check the caller

Most need a valid app token. The Telegram webhook checks its own secret header, and the public API its own key.

Only admins can send announcements

Since 30 October, an announcement needs an admin session or the server's own key, and one that would reach nobody is refused.

Church app keys

Stored only as fingerprints, limited to the areas an admin ticks, 60 requests a minute each, every request logged, and switched off in one tap.

Attendance can't be rewritten

After class only admins change marks. Moves in the two-absence review are recorded and can be undone the same day.

Secrets, backups and the wire

No secrets in the code

The repository is public, so keys live in Supabase's vault, GitHub's secrets and the team's Bitwarden vault, never in files.

Encrypted nightly backups

The whole database and its files, AES-256 encrypted before upload, kept 90 days. A second job restores each one to prove it works.

HTTPS everywhere

The app forces secure connections (HSTS, two years). Supabase, Vercel and Cloudflare all serve over HTTPS.

Analytics hide what people type

PostHog session replays mask every input. Test accounts and the Practice cohort are kept out of live numbers.

A few hardening items found in this check are being fixed. They are tracked with the owner, not on this page, because the code is public.

Making a change

Three kinds of change, three routes to live

Only the first goes live by pushing. Database changes and server functions are applied by hand, so the repo and the live system can drift if a step is skipped.

Screens and wording

  1. Read the latest handoff for that area
  2. Change frontend/src/
  3. npm run build passes (type check, tests, build)
  4. Try it in a browser as the role that uses it
  5. Commit, push to main

Live in about 2 minutes (Vercel)

Database

  1. Write a dated file in supabase/migrations/
  2. Apply it to the live database by hand
  3. Check it live, as each role
  4. Register any new rule in FLOW_MAP
  5. Commit the file

Live when applied; the file keeps the history

Server functions

  1. Edit supabase/functions/<name>
  2. Deploy with the Supabase CLI
  3. Note the version in the handoff
  4. Commit

Saving in the repo does not deploy it

Every commita Flow-Map: checked line, after re-reading FLOW_MAP section 4. The pre-push hook checks it.
Every finished piecea handoff in docs/handoffs/ and a row in its INDEX.
Every testuses test accounts, and you clean up what you made.
Every mistakeis undone with git revert and a push.
Rules that bite

The six that break things most often

The database enforces these. Screens only mirror them, so never re-create the logic in the frontend.

1

No form, no progress

Registered and beyond needs a sign-up form on file.

2

One current cohort

Defined once in the database. Never work it out again elsewhere.

3

One phone per cohort per name

Couples and teens may share a number. No email login: emails repeat.

4

Same-gender assignment

With a load cap from Settings. Quiet supports are skipped.

7

Phone numbers normalised

Nigerian mobiles saved as 080…; bad numbers held back, never dropped.

TEEN

Teens are protected

Ages 10 to 17: guardian signs in first, numbers hidden, API needs a separate permission.

Over a hundred rules in all, each pointing to the migration or function that enforces it: FLOW_MAP.md section 4. New tables start locked, with no open access.

Never do

Mistakes that can't be undone, or hurt quietly

✕
Change the push (VAPID) keys

Every phone stops getting notifications until each person turns them on again.

✕
Lose the backup passphrase

Without it, no backup can be opened. Keep it in the password manager.

✕
Delete tables, functions or jobs "while you're there"

Look at what uses it first, then get a clear yes for that one thing.

✕
Change the live database without a migration file

The repo then lies about what is live.

!
Testing touches real data

There is no test copy. Local development talks to the live database.

!
Vercel's free plan caps deploys per day

Batch your pushes. If capped, the site stays on the last good version; press Redeploy later.
